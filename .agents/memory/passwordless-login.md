---
name: Passwordless code login
description: Durable design lessons from replacing passwords with one-time codes in both account realms
---

- **Per-target send caps must be ONE shared pot across every code purpose.** **Why:** purpose-scoped counting lets one phone collect 3 login + 3 signup + 3 claim + 3 add-phone codes in the same hour — an SMS-bombing bypass reachable through any public endpoint. **How to apply:** the atomic ledger RPC counts recent sends by identifier alone and takes a purpose-less advisory lock; regression tests alternate rails for one identifier and assert the fourth total send stores nothing; capped responses stay byte-identical to real sends.
- **A one-time code needs an atomic claim between proof and reward.** **Why:** taking an attempt slot atomically but never claiming the row on success lets two concurrent verifies of the same code both mint sessions. **How to apply:** immediately after the code proves out, claim the row with one conditional UPDATE guarded on the claim columns still being null; a lost claim answers exactly like a wrong guess, and the claim lands BEFORE account/session work so later failure fails closed (code spent). Regression tests must park the winner mid-flight via a one-shot gate in the backend fake — same-tick bursts resolve too fast to reproduce the race.
- **Stored scope ids resolve by id lookup, never by re-parsing user-facing code formats.** **Why:** signup completion re-parsed the ledger's stored provider id through the code-format parser; production-shaped ids failed → 409 after a successful phone verify, and only live e2e caught it. **How to apply:** any handler consuming a stored scope_key/id uses an id-keyed resolver; test fixtures must use production-shaped ids, not conveniently code-shaped ones.
- **A staff login must provision workspace authorization atomically with the sign-in, every time.** **Why:** creating and linking the auth user without its role profile mints sessions that route to a placeholder screen — signed in but unusable — and identities created before the rail stay broken forever if only first logins provision. **How to apply:** one canonical service-role DB routine (role assignment + provisioning marker + role profile + roster link, single transaction) runs on EVERY proven staff code — first login and repeat alike, so it doubles as repair; the verify fails closed if provisioning fails, and an e2e must walk each staff class from code to a usable workspace, not just to a session token.
- **Live SMS acknowledgement must not weaken neutral account discovery.** **Why:** awaiting Twilio only for matched patients makes rejection status or latency an account oracle, while deleting rejected ledger rows bypasses send caps. **How to apply:** resolve the destination from the patient row, await provider acceptance behind the same fixed floor used for misses, keep rejection responses neutral, retain every registered row for quota accounting, and detach best-effort terminal marking from response timing.
