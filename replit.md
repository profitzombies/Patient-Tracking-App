# THINNR Med Spa Operations

Platform for the THINNR weight-loss program: a staff/HQ operations web app, a patient mobile companion (Expo), and an API server behind real Supabase sign-in. The original guided investor demo (persona pickers, guided walkthrough, mobile claim test) has been removed — see "No guided demo" below.

## Run & Operate


### No guided demo

There is no demo entry point in either app and no `THINNR_DEMO` switch (removed 2026-10-08). Signed-out web visitors only reach sign-in and the real public pages (training share links / the course preview, `/pay`, cancel links, `/security/report`, `/hq-setup`, `/email`); on mobile, first launch shows only real patient sign-in/sign-up/invitation and provider sign-in, and the patient routes admit real accounts only (no persona picker, no signed-out provider dashboard, no `/claim-test`). Signed-in screens never show demo labels, projections or seeded values — they show live data or an honest empty state. The training roster has no world-readable rows: the anon demo-read policies were dropped (`20261203000000_training_drop_demo_roster_policies.sql`); the `is_demo` column remains as a legacy seed marker only. Still pending clean-up (follow-ups): the seeded data modules and the signed-out branches that read them in the web office/HQ pages, the mobile hermetic suites that use the demo account as their baseline, and the API's demo patient grounding for tokenless coach/scan calls (removed once signed-out AI access is closed). Training media writes need an HQ sign-in (`content_manage`); only the learner reads (playback, transcript, attachment download) are open.

### Portable Stripe configuration

Stripe billing uses server environment variables only, with no Replit connector
fallback. Set a stable, deployment-specific `BILLING_DEPLOYMENT_ID` (distinct for
development and production); it namespaces the persisted HQ Test/Live selection.
Do not change or share it casually. New selections default to Test.

Configure `STRIPE_TEST_SECRET_KEY`, `STRIPE_TEST_PUBLISHABLE_KEY`,
`STRIPE_TEST_PLATFORM_ACCOUNT_ID`, `STRIPE_TEST_CONNECT_CLIENT_ID`,
`STRIPE_TEST_PLATFORM_WEBHOOK_SECRET`, and `STRIPE_TEST_CONNECT_WEBHOOK_SECRET`.
For Live use `STRIPE_LIVE_SECRET_KEY`, `STRIPE_LIVE_PUBLISHABLE_KEY`,
`STRIPE_LIVE_PLATFORM_ACCOUNT_ID`, `STRIPE_LIVE_CONNECT_CLIENT_ID`,
`STRIPE_LIVE_PLATFORM_WEBHOOK_SECRET`, and `STRIPE_LIVE_CONNECT_WEBHOOK_SECRET`.
The Connect client ID is needed only for OAuth; signing secrets belong to separate
platform/Connect destinations for each mode. Set `BILLING_PUBLIC_ORIGIN` to the
intended public HTTPS origin. Never put secret values in source, browser/mobile
build variables, logs, or `.replit`. See `docs/billing-connect/LAUNCH.md` for
destination URLs/events and launch checks.

Matching key prefixes and the authenticated platform identity are checked before
Stripe operations. No keys means payments are unavailable, not an application-wide
startup failure. Nullable legacy billing identities are quarantined: classify them
only after verifying the actual Stripe platform and mode, including related rows.
Do not assume legacy means Test, relabel records Live, or silently migrate financial
data. Sandbox records are usable only after verified classification.

The installed Replit integration is separate from runtime code. If the owner elects
to remove it, the documented manual path is **Integrations → Stripe → Manage →
disconnect**. We do not disconnect it automatically or claim this clears a Publish
gate; the owner must check the platform's current publishing requirements afterward.
Synthetic tests do not validate real Stripe credentials, webhook delivery, or live
account activation; those remain separate authorized checks after configuration.

## Authentication (Supabase)

Real Supabase auth is the front door on both apps. There is no guided demo and no way in without an account (see "No guided demo"); signed-in screens read live data or show an honest empty state.

- Client env vars (already set, client-safe publishable key; no service-role key in this workspace): `VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY` (web), `EXPO_PUBLIC_SUPABASE_URL` / `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (mobile).
- Roles come from the database-only `staff_role_assignments` allowlist. A confirmed email gets its listed `hq_admin` or `provider_staff` role; everyone else is a patient. Adding, updating, or deleting an assignment synchronizes matching confirmed profiles, and deleting an assignment revokes staff access. Add staff with the SQL documented in `docs/supabase-auth-setup.md`; do not edit `profiles.role` directly.
- Provider staff get an office **Training** area (`/training` in the office shell): their own progress with mark-complete, the live course catalog, the office roster, and self-serve teammate adds. Adding a teammate pre-approves the email in `staff_role_assignments` (HQ admins for any office, provider staff for their own only) — nothing is emailed; when that person first signs in with an email code, their account auto-links to a `training_viewers` row under the office (`supabase/migrations/20260827000000_training_staff_logins.sql`, proven live by `test:training-staff`). A signed-in staffer's whole office desk is scoped to their own office (real patients/roster stay synthetic; program data identical).

Suites: `claim.test.ts` (mocked), `claim-live.test.ts` (`RUN_CLAIM_LIVE=1`), `test:claim-flow` (mobile UI).
- **Patient session persistence (keep login codes rare)** (since 2026-09-18): every patient SMS code is a paid Twilio Verify message, so a patient on the same phone must stay signed in indefinitely under normal use. **Supabase auth session policy** (set through the management API `PATCH /v1/projects/{ref}/config/auth`; verify with GET, the dashboard shows the same fields under Authentication → Sessions): access-token `jwt_exp` 3600 s; refresh-token **rotation on** with a **30 s reuse interval** (was 10 s — a phone that retries a rotation over a flaky link must not get its whole session revoked); **inactivity timeout 4320 h = 180 days** (the management-API field is in *hours*, max 8760; the config.toml `inactivity_timeout` is a duration string); **no timebox** (0) and **no single-session-per-user** (a patient may keep a phone and a tablet). Why 180 days: the plan asks for ≥ 90 days of normal use without a code; the app refreshes the session on every launch/foreground, so only a real absence longer than six months forces a new code, while a lost phone's session still dies on its own. Sign-out therefore happens only on explicit sign-out, a security revoke ("sign out everywhere" / reported sign-in), a locally invalid token (definitive 400/401/403 from the token endpoint), or that six-month absence — never on a transient network/5xx failure. **App-side rule** (`artifacts/thinnr-mobile/lib/supabase.ts`): the stored session in AsyncStorage is authoritative for "still signed in"; auth-js reports `session: null` while a retryable refresh is failing (expired access token + network/5xx), so `useSupabaseSession` exposes `sessionStale` instead of signing out, `resolveSessionAccessToken` distinguishes `stale` from `signed_out`, and patient-data/coach/security requests surface a reconnecting error (`SESSION_RECONNECTING_MESSAGE`) rather than falling back to demo or clearing the account epoch. Only the `SIGNED_OUT` auth event clears the patient account. Suite: `test:session-persistence` (mobile; real auth-js against a scripted token endpoint — transient 5xx keeps the session, a definitive refusal signs out, a new device has no stored session, the same device after 60 days refreshes silently). **Verification metric:** `auth_sign_ins` already records the method of every sign-in; `hq_patient_sign_in_metrics(p_months)` (service-role RPC, `supabase/migrations/20261027000000_patient_sign_in_metrics.sql`) joins it per UTC month with `patient_app_presence`, the hourly `patient-sign-in-metrics` job logs the numbers each tick, and `GET /api/hq/system-health` carries them as `patientSignIns` (null = ledger unreadable, shown as "unavailable", never zero) for the **Login codes per active patient** panel on HQ System health.
- **Bearer tokens are verified locally, not per request in Supabase Auth** (`artifacts/api-server/src/auth/`). `access-token.ts` checks the JWT's signature against the project's published JWKS (cached, refreshed once on an unknown `kid`), expiry, issuer, and audience; `identify.ts` then refuses any token whose `session_id` is on the server's revocation list (`auth_session_revocations`, migration `20261027000000`) — one indexed lookup, rows carry their own expiry (`AUTH_REVOCATION_ROW_TTL_SECONDS`, default one week = Supabase's longest JWT lifetime) and the `retention-session-revocations` job sweeps them. `verification-policy.ts` is the ONE place that decides which route families still confirm the session **remotely** (`GET /auth/v1/user`, one jittered retry on timeouts/5xx, never on 401/403): billing writes (money moves), privacy/deletion (consent, exports, account deletion), and security settings (`/security/*`, office/HQ session lists and forced sign-outs) — there, even a session ended straight in the Supabase dashboard or a deleted user bites instantly. Everything else is local; the revocation list is checked on both paths. Non-JWT/HS256 tokens and tokens the JWKS cannot vouch for fall back to the remote lookup. Every server-side sign-out (HQ/office forced sign-outs, "sign out other devices", recovery sweeps, purge) goes through ONE atomic RPC, `security_revoke_auth_sessions` (migration `20261027000001`): in a single statement it lists every targeted `auth.sessions` row on the revocation list (no row cap, expiry computed in SQL) and deletes those rows (refresh tokens cascade) — this project's GoTrue serves no `/admin/users/{id}/logout` route, so deleting the sessions is how GoTrue's own global logout works. A refused RPC signs nothing out and the API reports failure rather than "signed out". Locked/disabled staff are still refused by the existing database lock check. Suites: `src/auth/*.test.ts`, `routes/security.test.ts` ("local token verification"), `routes/auth.test.ts`.
- Email confirmation is ON and Supabase's built-in mailer is rate-limited (a few emails/hour) — fine for the demo accounts, not crowds. Toggle: Supabase dashboard → Authentication → Sign In/Up → "Confirm email". Confirmation links bounce to the Site URL (Authentication → URL Configuration) — add the app URL there so links land back in the app.
- **Passwordless sign-in, both realms** (since 2026-08-30, task 369): daily login has no passwords anywhere. Staff (HQ + provider offices) sign in on web with business email + 6-digit emailed code; patients sign in on mobile with cell phone + texted code (email-code fallback via "Use email instead"), and mobile signup runs provider code → phone code → email, creating a real patient row in the office roster. Codes ride the `claim_verifications` ledger (10-min expiry, 5 attempts, 3 sends/hr per address/number shared across every code purpose — login, signup, claim, add-phone draw one pot, neutral about account existence, locked accounts get nothing); the server verifies a code then mints a session via GoTrue magiclink token-hash; patient logins use synthetic emails `pt-<patientId>@patients.thinnr.invalid`. Web remembers a device ~30 days (`thinnr-ops-code-login-at` in localStorage); mobile stays signed in until sign-out. Delivery modes: `CLAIM_EMAIL_DELIVERY_MODE` / `CLAIM_SMS_DELIVERY_MODE` — `dev` (default outside production) shows codes in-app, `live` needs Resend + Twilio Verify secrets. Provider accounts carry a required contact-only **Office phone** (never a login field — the owner's personal cell stays free for their own patient account). Suites: `routes/auth.test.ts` + `src/auth` (api-server), `test:patient-auth` (mobile), `verify-staff-logins.ts` (ops live).

**How the split is configured**
- `.replit` env vars: `[userenv.production]` holds the production values for `VITE_SUPABASE_*`, `EXPO_PUBLIC_SUPABASE_*`, `TRAINING_OBJECT_DIR`, `OPERATIONS_APP_URL`, `JOBS_DISABLED=1`, `NOTIFICATIONS_DISABLED=1`, and `SYSTEM_ALERT_EMAILS=on`. `[userenv.development]` points `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `VITE_*`, `EXPO_PUBLIC_*`, `TRAINING_OBJECT_DIR`, and `PRIVATE_OBJECT_DIR` at development, and sets `BILLING_DEPLOYMENT_ID=thinnr-development` plus `NODE_OPTIONS=--import /home/runner/workspace/scripts/dev-environment.mjs`.
- Shared **secrets** keep their production values; the published app reads them from Publishing → Production app secrets. Development values live in `DEV_*` secrets (`DEV_SUPABASE_SERVICE_ROLE_KEY`, `DEV_STRIPE_TEST_PLATFORM_WEBHOOK_SECRET`, `DEV_STRIPE_TEST_CONNECT_WEBHOOK_SECRET`). The `scripts/dev-environment.mjs` preload copies each one over its canonical name in every workspace Node process. A missing `DEV_*` value removes the canonical name instead of falling back to production. The preload also unsets `BILLING_PUBLIC_ORIGIN`, so Stripe return links use the workspace domain, and the live warehouse settings `WAREHOUSECRAFT_TENANT_MODE` and `WAREHOUSECRAFT_API_*`, so development always falls back to the `NOVEX_API_*` test tenant and can never submit a real warehouse order. **It refuses to start (exit 78) any workspace process whose Supabase URL still names the production ref.** Deployments set `REPLIT_DEPLOYMENT=1` and skip it.
- Never give the published app development keys. Before any republish, check that Production app secrets still hold the production `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `PRIVATE_OBJECT_DIR`, `BILLING_DEPLOYMENT_ID`, and `NOTIFICATIONS_INTERNAL_TOKEN`, and do not list `SYSTEM_ALERT_EMAILS`. The API server also guards this: in a deployment it refuses to start if any Supabase URL names the development ref, an object dir is a `dev/` prefix, or `BILLING_DEPLOYMENT_ID` is `thinnr-development` (`src/lib/deployment-environment.ts`). A refused start fails the publish and leaves the previous version serving.
- Stripe test mode has separate webhook destinations. Production uses `https://app.trythinnr.com/api/billing/webhooks/test/{platform,connect}`. Development uses the main workspace dev domain (`…-00-hqogufpgvrsz.kirk.replit.dev/api/billing/webhooks/test/{platform,connect}`). Each destination has its own signing secret: the dev ones are the `DEV_STRIPE_TEST_*` secrets. Stripe sends every test-mode event to every test destination. Production's test endpoint therefore also logs development's test events in its webhook inbox. Those events match no production office or order.

## Architecture decisions

- Real auth is the only front door: the Supabase session and role decide which workspace you land in. No demo persona exists; signed-out visitors reach only sign-in and the public pages.
- **HQ Training is the one live-data area**: courses/modules/videos/viewers/completions live in Supabase (`supabase/migrations/20260825000000_training.sql`; assembly + analytics in `artifacts/thinnr-operations/src/data/hq/training.ts`, react-query layer in `src/contexts/training-data.tsx`). Catalog reads (courses/modules/videos) are open to the anon key; viewer/completion/invite rows are never anon-readable (the `is_demo` read policies were dropped in `20261203000000_training_drop_demo_roster_policies.sql`) — registrations are visible to real HQ admins and, for their own office, provider staff. Authoring writes require a real signed-in `hq_admin` (RLS) — demo personas browse read-only with a banner and a "sign in to make changes" nudge. The learner preview's email gate, staff invites, and mark-complete go through narrow SECURITY DEFINER RPCs keyed by an opaque per-registration session token (`training_learner_sessions`, readable by no role), never by caller-supplied viewer ids (`supabase/migrations/20260826000000_training_learner_privacy.sql`; boundaries proven live by `test:training-access`). Lesson videos can carry a **real hosted file**: HQ admins upload MP4/WebM/MOV (≤500 MB) from the video editor's Media card straight to Replit App Storage via presigned PUT URLs minted by the API server (`artifacts/api-server/src/routes/training-media.ts` + `src/lib/objectStorage.ts`), which verifies the caller's existing Supabase staff session and role on every call (`src/lib/staff-auth.ts` — hq_admin authors; hq_admin + provider_staff stream). Playback rides short-lived signed GET URLs (range requests hit storage directly, so seeking works); the DB stores only object paths (`training_videos.video_source`, `thumbnail_source`), never URLs. After an upload the server runs an AI pass with per-step SSE progress — ffmpeg pulls the audio, the AI integration transcribes it in one-minute chunks (`training_video_transcripts.segments`, HQ-only reads per `supabase/migrations/20260829000000_training_video_hosting.sql`), the model writes the description + chapter list from the timed transcript; every result is editable, failures surface plainly with retry, and the file stays hosted regardless. The thumbnail doesn't wait for that pass: finalize captures the video's first frame the moment the upload lands (the AI pass's thumbnail step runs only as a retry when the instant capture failed), and admins can still scrub to capture any other frame. The Media card's whole "Video file" section is one drag-and-drop target — dropping a file uploads immediately, dropping onto a lesson that already has a video replaces it with no confirmation (the old video + thumbnail objects are deleted), a window-level guard keeps missed drops from navigating the tab into the file, and a re-check of `video_source` right before persisting any captured thumbnail drops stale frames from a just-replaced file. Training media resolves through `TRAINING_OBJECT_DIR` (`/<bucketId>/.private`, the dedicated training bucket) when set, falling back to `PRIVATE_OBJECT_DIR`; stored object paths don't name a bucket, so only change that knob while no hosted files exist — or migrate the objects first. Editor + office lesson pages swap in a real player (`src/components/training/HostedVideoPlayer.tsx`) when a file exists; lessons without one keep the simulated workbook slides, as does mobile (deliberately no mobile playback — it carries the columns for row parity only). Seeded demo lessons ship file-less on purpose; attachments stay name-only metadata. Provider-staff sessions additionally read their own office's viewer/completion rows via additive RLS (own row or same `provider_account_code`, resolved by `private.caller_provider_account()`), and act through two auth-keyed SECURITY DEFINER RPCs — `training_add_staff` (self-serve roster adds) and `training_mark_video_complete_self` — added in `20260827000000_training_staff_logins.sql` and proven live by `test:training-staff`. The office-side lens (`src/data/office-training.ts` + `OfficeTraining`/`OfficeTrainingCourse` pages) reuses the same snapshot and HQ math, pinned by section 11 of the invariants suite.
- **Push notifications are a service-only outbox** (`supabase/migrations/20260927000000_push_notifications.sql`; server code in `artifacts/api-server/src/notifications/`). Every server-originated patient push is a `patient_notifications` row; the in-process worker (and `POST /api/internal/notifications/tick`, bearer `NOTIFICATIONS_INTERNAL_TOKEN`) drains due rows through the `claim_patient_notifications` lease RPC in a looping tick (adaptive claim size 10–200, ~20 s budget per tick via `NOTIFICATIONS_TICK_BUDGET_MS`, leases renewed at half-life, backlog + oldest-due age shown on HQ System health), sends via Expo 100 per request, records tickets/receipts and attempts, retires tokens Expo reports as not registered (`device_not_registered`) so later sends skip them, and enforces patient categories + quiet hours at send time with the suppression reason stored on the row. Real-account coach stall outreach is evaluated server-side (`stall-outreach.ts`, parity-tested against the mobile `assessNudge`) and seeded into the persisted coach thread as `coach-outreach:<crossingKey>`; staff read the outreach state on the roster (`provider_outreach_states` RPC) and the full timeline at `GET /office/patients/:id/notifications`. Mobile registers device tokens per account epoch (`lib/push-notification-core.ts`); Expo Go/web/simulator show honest unavailable states — device proof needs an EAS development build with `EAS_PROJECT_ID` (see `artifacts/thinnr-mobile/PUSH_NOTIFICATIONS.md`).
- **Patient privacy lifecycle is service-only and worker-driven** (`supabase/migrations/20260928000000_patient_privacy_lifecycle.sql`; server code in `artifacts/api-server/src/privacy/`). Consent is versioned by `CONSENT_POLICY_VERSION` (`privacy/consent.ts`) and recorded per patient with app version/platform; the mobile app redirects protected routes to `/consent` until the current version is satisfied (`lib/live-patient-entry.ts`). Data exports are `patient_data_exports` rows a worker turns into a private zip on the media rail with a short-lived signed download and a `data_export_ready` push. Account deletion is patient-initiated only: `POST /patient-data/deletion` starts a grace period (`PATIENT_DELETION_GRACE_DAYS`, default 7) during which any sign-in offers cancel; the purge worker then deletes storage prefixes, every `patient_id` table via the `patient_purge_rows` RPC (FK-ordered, idempotent), and the auth user, leaving a PII-free `patient_tombstones` row. Rosters show a grace chip and a "Deleted accounts" section, the record answers 410 for a purged id, and HQ reviews/retries failed purges at `/admin/audit/deletions` (`GET/POST /api/hq/patient-deletions`). Demo personas see all of this as unavailable. Suites: `privacy-api`, `privacy-controls`, `account-deletion` validation commands.
- **Scheduled clean-up runs through one job framework** (`supabase/migrations/20260929000000_system_jobs_and_storage_hygiene.sql`; server code in `artifacts/api-server/src/jobs/`). Named jobs (abandoned-upload sweep, two-way storage reconciliation, chat/notification/audit/export retention driven by organization policy) run under a DB lease that the scheduler heartbeat-renews for the life of the run; jobs call `ctx.checkpoint()` between units of work and stop if the lease is lost. Every run (scheduled, manual, internal tick, or user-triggered discard) lands in `system_job_runs` with counts and per-item failures; failures back off exponentially. Upload URLs register `storage_upload_intents`; reconciliation flags ledger rows whose object vanished (`object_missing_at` → UI "File unavailable", downloads 410). HQ → Manage → System health lists jobs, last success/failure, recent runs, Dry run and Run now (`settings` permission). `POST /api/internal/jobs/tick` shares the notification bearer (`NOTIFICATIONS_INTERNAL_TOKEN`); `JOBS_DISABLED=1` stops the in-process ticker (and the export/privacy worker loops) — see "Production background work" below for the autoscale posture.
- **Ledger retention** (`supabase/migrations/20261027000000_ledger_retention.sql`; jobs in `artifacts/api-server/src/jobs/definitions/retention.ts`). Three tables that used to grow forever are trimmed daily, each behind its own knob in the HQ policy "Data retention & exports" section (offices see them read-only): `retention-job-ledger` deletes `system_job_runs` older than **Job run history** (default 90 days) but always keeps the latest 50 runs per job (`KEEP_RUNS_PER_JOB`), item failures cascade; `retention-sign-ins` deletes `auth_sign_ins` rows older than **Sign-in history** (default 180 days) in ONE SQL statement whose guards never drop an account's latest active session, a row still backing a live GoTrue session, or a row whose "this wasn't me" token is unexpired; this window also bounds how far back the HQ patient sign-in metrics (`hq_patient_sign_in_metrics`, up to 24 months) can count, so months older than it read low by design; `retention-billing-webhooks` still nulls processed payloads after `BILLING_WEBHOOK_PAYLOAD_RETENTION_DAYS` (env, 90) and now also deletes processed, error-free `billing_webhook_events` rows older than **Webhook events** (default 365 days) — unprocessed or failed rows are never deleted. All three SQL functions (`retention_trim_job_runs`, `retention_trim_sign_ins`, `retention_trim_billing_webhook_events`) are service-role only, batched (500 × 20 per run), dry-run neutral, and their counts land in the run ledger. `artifacts/api-server/src/jobs/ledger-retention.sql.test.ts` proves the guards on a temp PostgreSQL.
- **Legal holds outrank every retention timer** (`supabase/migrations/20261107000000_legal_holds.sql`; server `artifacts/api-server/src/routes/hq-legal-holds.ts`; HQ UI `artifacts/thinnr-operations/src/pages/admin/LegalHolds.tsx` + `src/components/admin/LegalHold.tsx`). One `legal_holds` table holds patient- and office-level rows; `legal_hold_active(patient_id)` (also resolves through the patient's office) is called INSIDE the delete statements of the chat trim, audit compaction, notification/sign-in/job-ledger/webhook trims, storage reconciliation, and the purge claim, so held rows are never selected. A pending deletion request parks as status `held` (patient app still sees "pending") and resumes its grace clock on lift. HQ Admin/Super Admin place and lift with a required reason (`POST /api/hq/legal-holds`, `POST /api/hq/legal-holds/:id/lift`; audit `legal_hold_placed` / `legal_hold_lifted`); HQ → Audit → Legal holds lists them; controls sit on the office account page and the drill-in patient record; offices only see a read-only "Legal hold" chip (computed column `patients.legal_hold`). Suites: `legal-holds-api` / `legal-holds-web` validations.
- **Production background work rides an external tick, not process timers** (since 2026-09-18). Production is an autoscale deployment (`.replit` → `deploymentTarget = "autoscale"`): the API server sleeps when idle and may run as several copies, so reminders, staff digests, exports, purges, and retention must not depend on `setInterval` inside one process. Posture: every scheduled loop is OFF in production and a scheduled trigger POSTs the two internal tick routes every minute. Development is untouched (flags unset → in-process tickers run as before).
  - **Production secrets** (Publishing → deployment secrets; values never in the repo): `JOBS_DISABLED=1` (stops the job scheduler AND the export + privacy worker loops), `NOTIFICATIONS_DISABLED=1` (stops the notification sender loop), `NOTIFICATIONS_INTERNAL_TOKEN` (long random bearer; the single secret both internal routes check in constant time — unset = the routes answer 404).
  - **The routes**: `POST /api/internal/jobs/tick` (bearer) drains office exports, patient exports, and pending purges in isolation, then runs every due job; body `{ job, dryRun }` forces one job, `{ drains: false }` skips the drains; 429 while another tick holds the in-process lock. `POST /api/internal/notifications/tick` (same bearer) runs one sender pass (outbox, staff outbox, stall outreach, missed doses, renewal reminders). Both await a heartbeat row in `system_external_ticks` (migration `20261027000000`, service-role only, one row per kind) before answering, so a paused autoscale instance cannot lose it.
  - **The trigger**: `node artifacts/api-server/scripts/external-tick.mjs` (plain Node, no build) POSTs both routes in order and exits 1 if either fails (429 counts as fine). Env: `INTERNAL_TICK_API_URL=https://app.trythinnr.com/api`, `NOTIFICATIONS_INTERNAL_TOKEN` (same value as the API deployment), optional `INTERNAL_TICK_TIMEOUT_MS` (default 240000). **Production's trigger (since 2026-10-05) is pg_cron inside the production database**: job `thinnr-external-tick`, `* * * * *`, two `net.http_post` calls with a 240 s timeout, bearer read from Vault secret `thinnr_internal_tick_token` (rotate with `vault.update_secret`). Inspect with `select * from cron.job_run_details order by start_time desc limit 5` and `select status_code, created from net._http_response order by id desc limit 5`. One minute is the pg_cron floor, so the 5-minute staleness threshold stays. A Publishing **Scheduled Deployment** running the script above is an equivalent alternative. Any external HTTP cron (Cloud Scheduler, cron-job.org, a GitHub Actions schedule) is an equivalent trigger: two POSTs with `Authorization: Bearer <token>`, ≥4-minute request timeout, once a minute. Multiple triggers or overlapping runs are safe — DB leases and the tick lock dedupe work.
  - **Health**: HQ → Manage → System health has an "External trigger" card: last tick time per kind, owner, counts, last error; a tick older than 5 minutes (`GET /api/hq/system-health` → `externalTrigger`, `staleAfterMs` 300000) shows a red warning when this server runs no timers of its own (production), only an amber note when it does (development, where a missing trigger is expected).
  - **Rotating the token**: set the new value on the API deployment and the scheduled deployment in the same sitting, republish the API first, then the trigger; expect at most one failed tick (401) in between, visible on the System health card. Never paste the token into chat, tests, or `replit.md`.
  - Suites: `src/jobs/external-trigger.test.ts` (ledger proof: `JOBS_DISABLED=1` + a due job runs only on the external tick, trigger `internal`, drains run, heartbeat lands; dev keeps the ticker), `src/jobs/external-tick-script.test.ts` (the real script against a local server: bearer, order, 429 vs 5xx, missing env), `src/routes/system-jobs.test.ts` + `src/routes/patient-notifications.test.ts` (secret required, drain isolation, heartbeats, health payload), `src/jobs/schema.sql.test.ts` (real-PG table constraints + service-role-only grants), `test:system-health` (ops card states). Validation commands: `external-trigger-api`, `system-health-web`.
- **Request speed, slow queries, and data growth live on HQ → Manage → System health** (`supabase/migrations/20261029000000_system_performance_metrics.sql`; server `artifacts/api-server/src/lib/request-metrics.ts`, `src/lib/request-timing.ts`, `src/system/`, `src/jobs/definitions/data-growth-snapshot.ts` + `system-thresholds.ts`; page `artifacts/thinnr-operations/src/pages/admin/SystemPerformance.tsx`). **How to read the page:** the three panels come from `GET /api/hq/system-health/performance` (separate from the jobs board; each section is null = "unavailable" on its own, never zero). *Request speed*: p50/p95/max per **route family** (the first two path segments after `/api`, ids collapsed, e.g. `office/roster`, `coach/chat`) for the last hour and last day, with request count, error share, and how many requests touched the database or an AI model. Every API response is also logged as `request completed` with `route`, `family`, `status`, `durationMs`, `db`, `ai`; anything over its family's amber budget logs `slow request` at warn. Timings are recorded in an in-process histogram and flushed once a minute (closed minutes only, poked from the request path so no timer is needed) to `api_request_metrics` as per-instance rows that the `hq_request_latency` RPC sums on read; rows older than 7 days are trimmed by the snapshot job. *Slow statements*: `pg_stat_statements` (enabled through the management API) read by the `hq_slow_statements` RPC, top 15 by total time and by mean time with calls, rows, and the reset time; statistics accumulate since the last reset, so a statement that was heavy last week still ranks until `pg_stat_statements_reset()`. *Data growth*: the daily `data-growth-snapshot` job writes table + index sizes, row estimates, and object-storage bytes per top-level prefix into `system_size_snapshots` (kept 400 days); the panel shows today's database and storage totals, the change since the previous snapshot normalised to one day, a history sparkline, and the biggest tables. A storage prefix that cannot be listed is an item failure and the storage total is withheld for that day rather than under-counted. **Thresholds** (one evaluator, `src/system/thresholds.ts`, colours the page and drives the alert; the effective limits are printed on the page): p95 latency over the last hour per family, **amber ≥ 1500 ms, red ≥ 4000 ms** (`LATENCY_AMBER_MS`/`LATENCY_RED_MS`); streaming families (the `STREAMING_FAMILIES` set in `request-metrics.ts`: coach chat/photo/recipe/menu-scan/label-scan, support chat, the staff inbox stream, internal ticks, training video uploads) use **20 s / 45 s** (`LATENCY_STREAM_*_MS`) because the response legitimately stays open while the model talks; the two inbox SSE feeds are long-lived subscriptions (open as long as a tab is open), so they get their own three-segment families `office/conversations/stream` and `hq/conversations/stream` (`LONG_LIVED_FAMILIES`) with no budget at all: never logged slow, never a finding, and never mixed into `office/conversations` / `hq/conversations`; families with fewer than 20 requests in the hour (`LATENCY_MIN_REQUESTS`) are never flagged. Database growth **≥ 250 MB/day amber, ≥ 1 GB/day red** (`DB_GROWTH_AMBER_MB`/`DB_GROWTH_RED_MB`); object storage **≥ 2 GB/day amber, ≥ 10 GB/day red** (`STORAGE_GROWTH_*_MB`). Amber means "look this week", red means "act now"; both are informational, nothing throttles. The 15-minute `system-thresholds` job evaluates the same numbers and queues an HQ staff alert email (`staff_notifications` kind `system_threshold`, `provider_id` null, sent through the templates library) to HQ settings managers, at most once per metric + family + level per UTC day, and logs `system_thresholds` on every run. `SYSTEM_ALERT_EMAILS=off` (set in the development environment only) mutes those emails while keeping the findings on the page and in the run log (`system_threshold_emails_muted`, tally `alertsMuted`): the shared dev server also carries the automated test load, which crosses the production latency limits by itself. Production leaves it unset (on). **Database read retries:** `supabaseAdmin` classifies each call as read (GET/HEAD, or a POST to an RPC on the read-only allow-list) or write; reads that fail transiently (timeout/abort/network error, or 502/503/504) are retried once after 100–300 ms of jitter; writes and data-changing RPCs are never retried automatically (they are covered by idempotency keys and CAS instead). Suites: `src/lib/supabase-admin.test.ts` (writes never retried), `src/lib/request-metrics.test.ts`, `src/system/*.test.ts`, `src/jobs/definitions/data-growth-snapshot.test.ts`, `src/jobs/definitions/system-thresholds.test.ts`, `src/alerts/staff-sender.test.ts`, `src/routes/system-jobs.test.ts`, `test:system-health` (ops panels). Validation commands: `system-performance-api`, `system-health-web`.
- **Patient writes are offline-first for real accounts** (mobile: `artifacts/thinnr-mobile/lib/patient-write-queue.ts` + `context/PatientContext.tsx`; server: `artifacts/api-server/src/lib/idempotency.ts`, `supabase/migrations/20260929000000_patient_write_receipts.sql`). Every diary/water/check-in/target/preference/library/flag/photo write is applied optimistically and appended to a persisted, per-account queue that replays strictly in order on reconnect/foreground with exponential backoff; after `maxAttempts` (or any 4xx) the item parks as failed with Retry/Discard in the sync sheet (`components/patient/SyncStatusChip.tsx`, chip on the patient tabs: offline / syncing / up to date / needs attention). ## Gotchas

- **Mobile web preview must mimic native iOS sizing and styling (permanent rule).** The Expo app on web always lays out at the iPhone reference width (393pt) on a fixed canvas that the root `WebFitShell` (`artifacts/thinnr-mobile/components/WebFitShell.tsx`, wired in `app/_layout.tsx`) scales to fill the preview frame — proportions match a real iPhone at every pane width. All future mobile UI work follows this: never hand-tune per-platform font/spacing values to "fix" web, and never call `useWindowDimensions` from `react-native` directly in mobile app code — use `hooks/useAppWindowDimensions`, which reports the canvas size (RNW `onLayout` already measures in canvas px). Likewise never import `Modal` from `react-native` in app code: RNW portals it to `document.body`, outside the canvas — use `components/ui/AppModal`, which re-applies the fit canvas inside the modal (native behavior identical). Width-pinned tests and debugging can force another canvas width with `?layoutWidth=<px>` (e.g. `360` to reach the Today hero's narrow steps) or disable the shell with `?layoutWidth=off`. Native iOS/Android rendering is untouched.
