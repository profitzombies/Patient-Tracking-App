# Patient shop checkout (server)

- **Claim, then rows, then money.** A checkout first claims its cart key with a primary-key insert (one patient per key), inserts every order/subscription row on ids DERIVED from (cart id, group index), and only then charges each group independently with the one saved card.
  **Why:** a read-then-insert idempotency check is racy and a crash between inserts leaves a partial cart that a replay would treat as complete; deterministic ids + Stripe idempotency keys derived from them make retries and duplicates land on the same rows and the same charges.
  The key is bound to a fingerprint of the REQUEST (lines + address + card), never of prices: the priced plan is persisted with the claim and a resume runs on the stored plan (Stripe price ids pinned to the row before create). Fingerprinting prices locks a stranded cart out after a price change while Stripe may already hold the charge. Resolve an existing key BEFORE catalog/live-account checks (replay/resume must survive archive, disabled subscription, below-minimum price, office disconnect). Cadence change = interval change: Stripe resets the anchor and bills now unless billing_cycle_anchor:"unchanged" rides with proration_behavior:"none". Replays re-read pending PaymentIntents. Pin the Connect account id on the claim: idempotency keys are account-scoped, and every other billing path (webhooks, reconcile, refunds) ignores accounts that are not the office's CURRENT one, so a cart stranded across an account swap must be made terminal (void unpaid objects on the old account, fail rows, 409 if something already paid) rather than charged on either account.
  **How to apply:** any new multi-row checkout path (staff orders, QR carts, Tap to Pay) must reuse the claim + derived-id pattern (child rows too, e.g. order items); never mint random row ids inside a retryable checkout.
- **Nothing is paid until every group is finalized and the SUM is checked.** Checkout is two-phase: finalize every group's Stripe invoice (one-time invoice, each incomplete subscription's first invoice), sum what Stripe actually finalized across paid-earlier and open groups, and refuse (void open one-time invoices, CANCEL incomplete subscriptions rather than voiding their invoice, fail rows with the total-changed message, definite) whenever the sum exceeds the authorized amount; only then pay group by group. Tax is estimated per group (own shipping line) before the claim because Stripe rounds per invoice.
  **Why:** the pre-claim 422 only sees the estimate; per-invoice tax rounding or a rate change between quote and finalize can make the billed sum exceed what the button showed, and a group-by-group pay would have charged the first group before discovering the second was over. Voiding a subscription's first invoice directly makes Stripe cancel the sub behind the app's back.
  **How to apply:** payer pages that cannot know tax (public prebuilt carts) bind the PRE-TAX shown total instead; a resume may therefore pay two groups where a stranded first attempt paid none. Test fakes do not replay idempotency keys, so a resumed create yields a new fake object.
- **Only a definite Stripe answer fails a line.** A decline, or an invalid request raised before any Stripe object existed, marks the order failed; connection/API errors (price mirroring included) and ANY error after Stripe returned an object re-throw so the order stays pending and the cart resumable. An already-settled invoice is read back as paid.
  **Why:** marking failed on an ambiguous error can report a charged subscription as failed; reconcile only heals rows that still say pending. Classify by "did Stripe answer", not by error type alone.
- **Every new billing table with patient_id must be classified for purge explicitly** (the purge RPC skips billing_% by design): accounting rows anonymize, transient rows (carts) delete; join the identity write guard; never store address/card data in transient rows.
- **One payer row per patient per office is a DB constraint, not a read-then-insert.** Resolve with insert-or-reread on the partial unique index; the Stripe customer stays single because its idempotency key is payer-keyed. Test fakes need an idempotency layer on customers.create to model this.
- **Patient reads scope by patient AND current office**, not patient id alone (patients move between practices).
- **Break-even is checked on the price actually charged.** Subscription lines and plan changes compare the discounted unit, not the office list price.
- **Shipping once per group.** One-time order shares one shipping charge; each subscription line is its own subscription with its own shipping line.
- **Shipments are a separate row** that mirrors the legacy fulfillment columns on every write; staff readers keep reading the order. "Delivered" mirrors as "shipped".
- **Move-next = Stripe trial_end (no proration); skip = move-next by one cadence.** Stripe's "trialing" maps to "active" so staff never see a new status.
- **Card removal re-points every subscription that names the card** (subscription-level default included) BEFORE detaching; the last card can't go while a subscription renews.

# Patient shop checkout (mobile client)
- **Ambiguous vs definite is the whole retry contract.** Only a checkout RESULT body or a client 4xx other than 408/409/429 is definite (new cart id next tap). Network, timeout, 5xx, an unreadable throw, and a failed device-side 3DS step are ambiguous: replay the SAME cart id AND the SAME request. A `partial` answer is definite but names paid items; their lines leave the cart before any retry.
  **Why:** the server replays a claimed cart id; a new id after an ambiguous answer double-charges, a reused id after a definite one re-sends stale prices. Money calls need their own deadline (real confirmations run 15–40 s; the shared 15 s rail aborts them), and an aborted client leaves the server finishing the charge, which is why timeout stays ambiguous.
- **The attempt is on disk before the POST leaves; settling it is ONE strict write.** Commit = strict write + byte read-back of (cart id, exact request, authorized quote); fail closed inline if the device cannot store it. Settle = pruned lines AND cleared attempt in a single write; on write failure the attempt stays on disk and replays as already paid. While unsettled the cart is locked (every mutator refuses) and the screen shows a frozen confirm view.
  **Why:** two writes, or a state-only clear, leave a paid line replayable or an attempt cleared while its lines stay after a crash between them; a commit and a clear in one render batch never trigger the persist effect.
- **A pay attempt is bound to the account that tapped, end to end.** Capture the cart scope (account-keyed store) and the session user BEFORE the first await; re-check after card tokenizing, after the commit, and before the POST; send under a bearer captured at that last check, never one resolved inside the request rail; a settlement that lands after a switch writes only to the attempt's own store key and never moves shared state. An attempt committed but refused before sending is taken back off its own store.
  **Why:** the card sheet and the 90 s checkout call both outlive a sign-out or account switch; without the binding the first patient's cart could be charged under the second's identity, or the late answer could prune the second patient's cart. Same rule as the device-integration epoch pattern.
  **How to apply:** test the switch at every await (tokenizing, session lookup, server answer) with a second scripted identity whose whoami resolves to a different patient; prove by mutation that the bearer test catches token-at-POST resolution.
- **The displayed total rides with the request, and pre-tax is never shown as the amount charged.** `expected_total_due_cents` is validated on a FRESH claim only (422 → definite, re-quote); replays are covered by the request fingerprint. Tax offices get a server estimate once an address is in; Pay stays disabled until the amount due is known.
- **Definite Stripe refusals arrive in two shapes:** a checkout RESULT with failed items, or a plain `{error}` envelope on 402 (card refused at attach, before any order exists). Both are definite; only the first names paid items.
- **Keep the card SDK mounted (hidden) while a saved card is selected** so 3DS `handleNextAction` has an instance; a `requires_action` item with no client secret is ambiguous (same id, no second POST).
- **Live browser proof needs the one Stripe-connected sandbox office** with a throwaway activated patient; other harness offices are not connected and in-app Connect onboarding is captcha-blocked.
