# Staff inbox over patient chat threads

- **Workflow state is derived by a DB trigger, not by the API.** An AFTER INSERT trigger on chat messages moves a conversation open (patient turn) / waiting_patient (staff turn) and accumulates response-time totals. **Why:** the patient app persists rows through `ON CONFLICT ... DO UPDATE` upserts and re-upserts finalized rows (card/hidden flips); a row-exists upsert does not fire the INSERT trigger, so replays can't corrupt state, and the API never has to sequence two writes. **How to apply:** new status transitions from message traffic belong in the trigger; only explicit staff actions (assign/close/reopen) go through the API, and closing never blocks a patient turn from reopening.
- **Historic AI staff turns are compatibility-only; new human replies belong outside AI.** Preserve historical transcript bodies and their existing folding behavior, but never extend that folding to the separate business conversation. **Why:** the patient/business channel has a different privacy and participation contract, not merely a new display label. **How to apply:** AI reply actions open the human destination; do not copy old AI history or automatically add human history to grounding.
- **Patient attribution and office ownership have separate meanings.** Employee attribution is internal; patient-facing human messages use the business identity and Care Team. Retained human ownership does not follow patient reassignment, including in metrics. **Why:** following the patient's current office would disclose a different business's transcript or distort its counts. **How to apply:** review list, transcript, metrics, export, and delayed notification scopes together.
- **Retry identity includes the original business conversation.** Never resolve a pending message's recipient from the currently assigned office at retry time. **Why:** the same signed-in patient can change businesses without an account epoch changing; a stable message ID alone did not prevent a failed private message from being sent to the new business. **How to apply:** bind recipient, body, and retry ID together; reject a now-read-only recipient and test reassignment between failure and retry.
- **Unread counts come from the server, not sequence subtraction.** **Why:** message IDs have global gaps and include patient-authored turns, so subtracting a read marker can turn one unread team reply into hundreds. **How to apply:** preserve authoritative counts through refresh and explicit reads; regression fixtures should use sparse sequences and mixed senders.
- **Polling must not imply reading.** Explicit read advancement is separate from transcript fetches and audit payloads contain no text. Serialize initial marker creation as well as updates. **Why:** a lock on a nonexistent row cannot protect concurrent first reads; both can report a new read or let a smaller sequence win. **How to apply:** test overlapping first reads and clamp client high-water marks to committed messages.
- **Coach route tests share one per-process burst bucket.** The existing coach suite already spends the full per-IP burst, so extra requests added to the same process flake later tests with 429; isolate new request-making tests in their own module.
- **Auto-close is a read-time overlay, not a write.** HQ's conversation auto-close window is passed to the inbox RPCs as a cutoff instant; idle threads read as closed (`autoClosed`) while persisted status stays untouched, so policy changes reclassify instantly and a patient message reopens for free. An explicit staff status change bumps `updated_at` so a deliberate reopen holds.
- Metrics RPC with `null` provider = all non-disabled offices; the HQ overview and office overview both fail the whole overview (502) when the inbox RPC is down rather than showing zeros.
- **Prove private-helper RPCs under the actual service role.** A service-only public invoker function still cannot call into the private schema merely because its EXECUTE grant is correct. **Why:** postgres-only SQL tests passed while the same live PostgREST call failed with schema permission denied. **How to apply:** use narrow service-only definer entry points with fixed search paths, keep helpers private, and test with `SET ROLE service_role`.

## Care-team product suggestions (structured message attachments)
- Suggestions live on the message's `card` jsonb (`kind: product_suggestion`), snapshotted server-side from the PATIENT storefront offering (`officeOffering`), never from the office price list's `offered` flag — floor-priced catalog products are buyable, so the web picker reads the sale context for that patient. **Why:** a picker keyed on office price rows showed nothing for offices with no custom prices while the server accepted floor-price items.
- Bundles do NOT mint prebuilt-cart rows (those expire in ≤24 h); the mobile bundle screen re-quotes the snapshot lines live, shows a "prices changed" note when today's subtotal differs, and loads the cart before the normal checkout.
- Demo message snapshots must be priced from the demo storefront (catalog price × subscribe-save), or the bundle summary and checkout disagree with the card.
