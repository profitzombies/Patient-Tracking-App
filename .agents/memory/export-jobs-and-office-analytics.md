---
name: Export jobs and office-dimension analytics
description: Durable decisions behind the CSV export pipeline and the live office comparison / analytics ranges in the operations web app.
---

- **Office staff are always pinned to their own office; an explicit `office` in a request body or query is ignored, never rejected.** **Why:** rejecting would leak which office ids exist; pinning makes staff requests scope-safe by construction. **How to apply:** live scripts must assert the returned scope equals the caller's office (200/202 pinned), not 403. Only the provider directory is HQ-only; office comparison / audit / training exports for staff are single-office slices of the same generators.
- **Export files never hold clinical notes or message text; HQ patient-level rows need provider_manage on that office.** HQ without an office gets the aggregate comparison instead (400 "Choose an office" for patient_activity).
- **Expiry is a status transition, not just a timestamp:** the worker sweep flips rows to `expired` and nulls the object path after deleting the object; download-url of an expired row is 410, a foreign row is 404.
- **Live date-range mode:** the header range context has `mode: 'demo' | 'live'` derived from auth state. Demo keeps the fixed anchor; live clamps to device-today with a max window. Ranges that predate the dataset render "Unavailable" (null), never 0 — the SQL rollup returns null metrics when no office has rows in range.
- **Pure helpers live in React-free `src/lib/*` modules** (date-range-keys, office-analytics, sparkline-summary, export-jobs) so tsx verify scripts import them without a DOM. Keep new pure logic there, not in contexts/components.
- **Live roster status filter vs rollup "Active":** the live roster's status is operational (on_track/needs_attention/inactive/invited); the rollup's Active = activated accounts. Drill links use `status=active`, which the roster maps to "not invited" on live data. Any new drill target must match a filter the destination page actually implements — verify by e2e, the link resolving is not enough.
- **Metric contract = what the label says.** Engagement figures (engaged, logging/check-in patients, and the daily engaged series) use the TRAILING 7-DAY window ending on the range end / on each day, so the series' last point equals the headline; avg pounds lost counts active patients only. **Why:** review rejected a version where SQL counted range-wide activity and included invited patients under an "active" label. **How to apply:** when adding a metric, write the help text first and make the SQL, CSV header, OpenAPI description and live verify script assert that same sentence.
